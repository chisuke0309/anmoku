# 設計書の評価（関門2）：agent-design_v1.md

**判定：差し戻し**（重大6・中3・条件0・軽1）

評価に使った物差し：修正版の業務フロー（「仮」の行を含む。人の承認はまだ。承認したものとして評価した）と定義台帳。判定の規則は Python で固定（重大か中が1件でもあれば差し戻し、承認されていない定義に頼る部分が残るあいだは合格にしない）。

- [重大]（観点A）設計書 処理手順 2 追加工事「現場監督の判断で進めてよいと回答する。」
  - 問題：フローでは追加工事に「小さい追加（十万円以下）は現場で決める（仮）」「怪しいと思ったら課長に聞く（仮）」「追加工事を進めてよいかの確認（課長・仮）」「十万円超は施主に言う前に一声（仮）」という判断の経路がある。設計書は金額や状況を区別せず、常に現場監督が進めてよいと答えさせており、課長を経由する経路を扱っていない。未確定とも書いていない。
  - 根拠：フロー：追加工事を進めてよいかの確認（仮）／小さい追加（十万円以下）は現場で決める（仮）／怪しいと思ったら課長に聞く（仮）
  - 合格の条件：追加工事の可否は、十万円以下かどうか・怪しいかどうか・課長の確認の要否が確定するまでエージェントが断定しない。仮の経路は「仮・確認待ち」と明記し、課長（佐藤さん）への確認に回す作りにする。
- [重大]（観点A）設計書 処理手順 2 難あり物件の見積「見積への上乗せを提案する。ただし上乗せ額は確定させない。」
  - 問題：フローでは難あり物件について、見積前に予備費の額を営業が統括（課長）へ相談する（仮）。設計書はこの相談の経路を扱わず、エージェントが上乗せを提案して店長の最終承認に回している。予備費（contingency-fund）は台帳で未確定で、上乗せの基準も未確定。それでもエージェントが上乗せを提案する作りになっている。
  - 根拠：定義「予備費」＝回答待ち／根拠 04_sales_senior.md:12「それを予備費みたいな形で入れる。」
  - 合格の条件：難あり物件では、見積前に統括の課長（佐藤さん）へ予備費を相談する経路（仮・確認待ち）を案内する。上乗せの提案は、基準が確定するまでエージェントがしない。
- [重大]（観点B）設計書 処理手順 2 職人の割当「手配では優先客を先にすると回答する。」
  - 問題：優先のお客さん（priority-customer）は台帳で draft。処理手順2では「優先客を先にする」を確定した方針として答えさせている。一方、使う用語と未確定事項3では優先客を「定義未確定」としていて、設計書の中で食い違っている。
  - 根拠：定義「優先のお客さん」＝下書き／根拠 02_koumu.md:14「前から付き合いのあるお客さんとか、紹介で来たお客さんは、優先で回せって言われてる」 ほか1件
  - 合格の条件：優先客を先にする扱いは未確定・確認待ちと明記する。確定するまでエージェントは優先扱いを回答せず、課長（佐藤さん）に回す。
- [重大]（観点B）設計書 処理手順 2 追加工事／未確定事項 4「現場監督の判断で進めてよいと回答する。」
  - 問題：「小さい追加の境目（additional-work-small-threshold）」「怪しいと思ったら聞く（ask-when-doubtful）」「十万円超の一声（over-100k-heads-up）」は、台帳上で未確定または draft。設計書は未確定事項4で店長承認との関係だけを未確定としており、この3つは未確定と書かないまま、エージェントが「進めてよい」と当てはめている。
  - 根拠：定義「小さい追加工事と十万円の一声ルール」＝回答待ち／根拠 03_genba.md:30「その「小さい」がどこまでなのか、正直よくわかんなくて」 ほか4件
  - 合格の条件：3つの定義を未確定として未確定事項に載せる。確定するまで、エージェントは進めてよいと断定せず、課長（佐藤さん）への確認に回す。
- [重大]（観点D）テスト仕様 TC-03「現場監督の判断で進めてよいと回答する。追加工事の見積は現場監督が作成すると案内する。」
  - 問題：期待値の「進めてよい」は、小さい追加の境目や課長確認など、未確定または draft の定義に頼っている。正解が決まっていないテスト。
  - 根拠：定義「小さい追加工事と十万円の一声ルール」＝回答待ち／根拠 03_genba.md:30「その「小さい」がどこまでなのか、正直よくわかんなくて」 ほか4件
  - 合格の条件：期待値を、未確定であることを伝えて課長に回す内容に変える。または、定義が確定してから期待値を決める。
- [重大]（観点D）テスト仕様 TC-07「15%の上乗せを提案する。」
  - 問題：15%の根拠はどの定義にもない。上乗せの基準（予備費）は台帳で未確定。注意事項に矛盾の記載はあるが、期待値は未確定のままの数字になっている。TC-04 の「優先客を先に手配する」も、draft の定義に頼る。
  - 根拠：定義「予備費」＝回答待ち／根拠 04_sales_senior.md:12「それを予備費みたいな形で入れる。」
  - 合格の条件：TC-07 の期待値は、注意事項にある「具体的な率は示さず、店長の最終承認に回す」に差し替える。TC-04 も優先客の部分を未確定扱いにする。
- [中]（観点A）設計書 エスカレーション「店長（暫定。正式な窓口は要確認）」
  - 問題：判断する人が不在のときの動きが決まっていない。店長が不在のとき（TC-09 のような場合）に、承認や値引きの案件を誰が代わりに見るか、待つのかが書かれていない。課長が不在のときも同様。店長は暫定窓口だが、台帳で未確定事項の答えを持つのは課長（佐藤さん）。
  - 根拠：フロー：見積の最終承認（店長）／値引きの承認（店長）
  - 合格の条件：店長・課長が不在のときの代理の担当者、または待つ期限と再連絡の方法を決めて書く。未確定事項の正式な窓口を決める。
- [中]（観点A）設計書 処理手順 2 値引き／エスカレーション「可否をエージェントは判断しない。店長の承認に回すよう案内する。」
  - 問題：フローには、店長に上げる前の課長への事前相談（仮）と「値引きは先に課長に聞く（仮）」がある。設計書は店長の承認だけで、課長への事前相談という経路を扱っていない。店長の承認自体はフロー通りだが、仮の経路が抜けている。
  - 根拠：定義「値引きは先に課長に聞く」＝回答待ち／根拠 01_sales_junior.md:32「誰に聞くかって決まりがあるのかは、よくわかんないですけど」 ほか1件
  - 合格の条件：値引きの前の課長への事前相談を、仮・確認待ちとして設計書に載せる。確認が取れるまでは「店長の承認が必要。事前相談の要否は確認中」と案内する。
- [中]（観点A）設計書 処理手順 2 職人の割当「手配と工程表の作成は工務担当が行う。」
  - 問題：フローでは工程表の前提として「職人の割り振り判断（課長・仮）」がある。設計書は課長の判断を扱わず、工務担当だけを案内している。
  - 根拠：定義「仮で組む工程と納期変動」＝回答待ち／根拠 02_koumu.md:26「水回りは、この職人さんじゃないと、みたいなのがあるみたいで」 ほか2件
  - 合格の条件：職人の割り振りは課長（佐藤さん）の判断が前提になる可能性があると、仮・確認待ちで書く。割り振りの判断が絡む問い合わせは課長に回す。
- [軽]（観点A）設計書 処理手順 2 見積「見積作成は営業担当が行い、最終承認は店長が行うと案内する。」
  - 問題：現地調査（承認済み）は見積作成の前に必ず行うという決まりごと。見積の案内に現地調査が入っていない。
  - 根拠：定義「現地調査」＝承認済み
  - 合格の条件：見積の案内に「見積作成の前に営業担当が現地調査を行う」ことを加える。
