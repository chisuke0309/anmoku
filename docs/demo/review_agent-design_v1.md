# 設計書の評価（関門2）：agent-design_v1.md

**判定：差し戻し**（重大6・中4・条件0・軽0）

評価に使った物差し：修正版の業務フロー（「仮」の行を含む。人の承認はまだ。承認したものとして評価した）と定義台帳。判定の規則は Python で固定（重大か中が1件でもあれば差し戻し、承認されていない定義に頼る部分が残るあいだは合格にしない）。

- [重大]（観点A）設計書 処理手順 2．追加工事「現場監督の判断で進めてよいと回答する。」
  - 問題：フローでは追加工事を進める前に工事統括（仮）へ確認するタスクがあり、返答待ちも発生している。設計書はこの経路を扱わず、現場監督の単独判断で進めてよいと断定している。「小さい追加は現場判断でよい場合もある」という例外を、すべての追加工事に広げてしまっている。
  - 根拠：定義「小さい追加工事の上限(現場判断と一声かけの基準)」＝下書き／根拠 03_genba.md:30「小さい追加なら現場で決めていいって言われてるんです。」 ほか4件
  - 合格の条件：追加工事を進めてよいかの確認が工事統括（佐藤さん・仮）を経由することを、「仮・確認待ち」と明記したうえで扱う。現場監督だけで進めてよいと断定せず、確認先を案内する。
- [重大]（観点B）設計書 処理手順 2．職人の割当「手配では優先客を先にすると回答する。」
  - 問題：「優先客を先にする」は draft の方針で、一覧も指名職人や動かせない日の条件もない。設計書は「優先客」の該当判断だけを未確定とし、優先する方針そのものはエージェントが確定事項として回答している。フローでは優先の指示は工務の外から出る。職人の割り振りを決める工事統括（仮）の経路も扱っていない。
  - 根拠：定義「付き合いのある・紹介のお客さんは優先して工程を回す」＝下書き／根拠 02_koumu.md:14「前から付き合いのあるお客さんとか、紹介で来たお客さんは、優先で回せって言われてる」 ほか1件
  - 合格の条件：優先客を先にする方針が確認待ちであることを明記し、断定せずに人に回す作りにする。職人の割り振りは工事統括（仮）が決めるタスクがあることも案内に含める。
- [重大]（観点B）設計書 処理手順 2．追加工事／未確定事項 4「現場監督の判断で進めてよいと回答する。」
  - 問題：「小さい追加なら現場判断でよい」は draft の定義で、「小さい」の範囲も決まっていない。設計書は未確定事項4で店長承認との関係だけを未確定とし、現場判断の範囲そのものは未確定と書かずに、エージェントが回答に当てはめている。
  - 根拠：定義「小さい追加工事の上限(現場判断と一声かけの基準)」＝下書き／根拠 03_genba.md:30「小さい追加なら現場で決めていいって言われてるんです。」 ほか4件
  - 合格の条件：小さい追加工事の上限が未確定（答えを持つ人は佐藤課長）であることを明記し、金額や規模が分からないうちは断定せず人に回す作りにする。
- [重大]（観点D）テスト仕様 TC-03「現場監督の判断で進めてよいと回答する。追加工事の見積は現場監督が作成すると案内する。」
  - 問題：期待値の前半（現場監督の判断で進めてよい）は draft の定義に頼っていて、正解が決まっていないテストになっている。フローの仮の確認経路（統括・十万円超の一声）も確かめていない。
  - 根拠：定義「小さい追加工事の上限(現場判断と一声かけの基準)」＝下書き／根拠 03_genba.md:30「小さい追加なら現場で決めていいって言われてるんです。」 ほか4件
  - 合格の条件：小さい追加工事の上限と統括への確認が決まるまでは、期待値を「断定せず、確認先を案内する」に差し替える。見積作成が現場監督である点は approved なので残してよい。
- [重大]（観点D）テスト仕様 TC-04「手配と工程表の作成は工務担当が行い、優先客を先に手配すると回答する。」
  - 問題：「優先客を先に手配する」は draft の方針に頼った期待値で、正解が決まっていない。
  - 根拠：定義「付き合いのある・紹介のお客さんは優先して工程を回す」＝下書き／根拠 02_koumu.md:14「前から付き合いのあるお客さんとか、紹介で来たお客さんは、優先で回せって言われてる」 ほか1件
  - 合格の条件：優先客の方針が承認されるまでは、期待値を「工程表の作成は工務担当。優先客の扱いは確認待ちとして人に回す」に直す。
- [重大]（観点D）テスト仕様 TC-07「15%の上乗せを提案する。上乗せ額は確定させず」
  - 問題：「15%」は、予備費の金額も難あり物件の定義も needs_answer のまま、根拠なく置かれた数字。注意事項で設計書との矛盾と差し替え案は示されており、有効化前に直すことになっている。
  - 根拠：定義「予備費の金額」＝回答待ち／根拠 04_sales_senior.md:12「「じゃあ十五万見とこうか」とか言ってくれる」
  - 合格の条件：予備費の金額と難あり物件の定義が承認されるまで、期待値を注意事項の差し替え案（具体的な率は示さない）にしておく。
- [中]（観点A）設計書 エスカレーション「未確定事項に当たり、判断できない問い合わせ | 店長（暫定。正式な窓口は要確認）」
  - 問題：店長や工事統括が不在のときの動きが決まっていない。TC-09でも店長不在の依頼を店長に回すだけで、承認が止まったときの代行者や待つ間の案内が無い。
  - 根拠：定義「見積の最終承認」＝承認済み
  - 合格の条件：店長（および確認先の統括）が不在のときの案内先と、待つ間にエージェントがすることを決めて書く。
- [中]（観点A）設計書 処理手順 2．値引き／エスカレーション「可否をエージェントは判断しない。店長の承認に回すよう案内する。」
  - 問題：フローでは、値引きが入るときは店長に上げる前に工事統括（仮）へ相談するタスクがあり、差し戻しも起きている。設計書はこの手前の相談を扱わず、店長だけに回している。店長の承認は正しく扱えている。
  - 根拠：定義「値引きはまず聞く」＝回答待ち／根拠 01_sales_junior.md:32「「値引きはまず聞いときな」って言われたんで」 ほか1件
  - 合格の条件：店長に上げる前に統括（佐藤さん？・仮）へ相談する経路を「仮・確認待ち」と明記して案内に含めるか、確認待ちとして未確定事項に載せる。
- [中]（観点A）設計書 処理手順 2．追加工事「追加工事の見積は現場監督が作成する。」
  - 問題：フローには「十万円を超えそうな追加は施主に言う前に一声かける（仮）」という決まりごとがあるが、設計書に一切書かれていない。十万円超の追加でも、そのまま進めてよいと答えかねない。
  - 根拠：定義「十万円超の追加は施主に言う前に一声かける」＝下書き／根拠 03_genba.md:26「十万を超えそうなときは、施主さんに言う前に一声かけるっていう。」
  - 合格の条件：十万円を超えそうな追加は施主に伝える前に先輩（佐藤さん・仮）へ一声かける、という決まりを「仮・確認待ち」と明記して扱うか、金額が不明なら止めて人に回す作りにする。
- [中]（観点A）設計書 処理手順 2．難あり物件の見積「見積への上乗せを提案する。ただし上乗せ額は確定させない。」
  - 問題：フローでは、古い・状態が怪しい物件は、見積作成の前に工事統括（仮）へ予備費の額を聞くタスクがある。設計書は上乗せを自分で提案する作りで、予備費を統括に聞く経路が無い。上乗せ額を確定させず店長承認に回す点は慎重な側で問題ない。
  - 根拠：定義「予備費の金額」＝回答待ち／根拠 04_sales_senior.md:12「「じゃあ十五万見とこうか」とか言ってくれる」
  - 合格の条件：難あり物件・予備費の額は統括（佐藤さん・仮）に聞く経路があること（確認待ち）を明記し、エージェントが上乗せを提案せず、聞く先を案内する形にする。
