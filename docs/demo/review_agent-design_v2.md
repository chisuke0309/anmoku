# 設計書の評価（関門2）：agent-design_v2.md

**判定：条件つき合格**（重大0・中0・条件2・軽0）

評価に使った物差し：人が承認した業務フロー（「仮」の行を含む）と定義台帳。判定の規則は Python で固定（重大か中が1件でもあれば差し戻し、承認されていない定義に頼る部分が残るあいだは合格にしない）。

- [条件]（観点B）設計書 処理手順 3. 値引き 3 ／ 使う用語「値引きの基準」「値引きの基準は確認待ちで、答えを持つのは店長。」
  - 問題：台帳には「工事内容で削れるか・職人の手間的に下げて良いか」（discount-work-feasibility、答えを持つ人は佐藤さん）という別の未確定の判断がある。設計書は値引きの答えを持つ人を店長だけにしている。この判断は用語にも確認待ち事項にも出てこない。エージェントは自分で判断しない作りなので、当てはめの危険は小さい。ただ、問い合わせ元は佐藤さんに何を聞くのかが分かりにくい。
  - 根拠：定義「工事内容で削れるか・職人の手間的に下げて良いかの判断」＝回答待ち／根拠 01_sales_junior.md:20「工事の中身で削れるところがあるかとか、職人さんの手間的にここ下げても大丈夫か」
  - 合格の条件：「工事内容で削れるか・手間的に下げてよいか」を確認待ちの用語として足す。答えを持つ人は佐藤さんと書く。確認待ち事項にも追加する。
- [条件]（観点B）設計書 処理手順 3. 職人の割当・優先客 4 ／ 使う用語「優先客」「優先客の範囲は確認待ちで、顧客の一覧もない。」
  - 問題：台帳の priority-customer-and-schedule は、優先のお客さんに加えて「絶対ずらせない日」と「指名職人」も含む。設計書は優先客の範囲しか扱っていない。工程の組み直しで出てきそうな日程や指名職人の制約が、確認待ちとして示されない。
  - 根拠：定義「優先のお客さん・絶対ずらせない日・指名職人」＝下書き／根拠 02_koumu.md:14「前から付き合いのあるお客さんとか、紹介で来たお客さんは、優先で回せって言われてる」 ほか4件
  - 合格の条件：「絶対ずらせない日」と「指名職人」も確認待ちの項目に入れる。答えを持つ人は佐藤さんと書く。該当する問い合わせは佐藤さんに回す。
